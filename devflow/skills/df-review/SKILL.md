# df-review 评审

diff 小，问题才看得清。节奏 = 实施完一步 → 评审该步 → 通过再继续。

## 输入

- 参数：change-id 和/或步骤号（如 S2），或明确的 diff 范围。
- 无参数：取最近 design.md 中状态"完成"且评审列非"通过"的步骤；全部完成则评审全量 diff。
- 找不到可评审对象则询问用户，禁止凭猜测圈范围。

## 流程

1. 圈范围：git diff 对照 impl-log.md 该步改动点；超出该步范围的改动单独指出。
2. 读上下文：该步方案要点、验收标准、已采纳的 D 决策点。
3. 四层检查：
   - **设计一致性**：符合该步设计与决策点；无确认留痕的偏离按 P1。
   - **工程质量**：正确性、边界条件、并发与资源、错误处理、可读性。
   - **仓库规范**：AGENTS.md 等（如有）硬约束逐条对照。
   - **验收完备**：对照该步验收标准逐条核验，指出已验证什么、缺什么。

## 输出

- P0-P3 分级问题清单，每条带 `file:line` 证据与修复建议；无问题的层也要写"未发现"。
- 结论：可进入下一步 / 须先修复（阻塞 = P0/P1）。
- 收尾：通过则 design.md 该步评审列改"通过"；有问题保持现状并列清单等用户处置。

## 硬性约束

- 只报不改：修复走 `/df-implement` 后复审，评审者不亲手修。
- 证据先行：每条问题读码核实给 `file:line`，不确定的标"待确认"，不把猜测当结论。
- 语言跟随用户（默认中文）。
