# df-review 评审

小步评审是分步执行的价值所在：diff 小，问题才看得清。节奏 = df-implement 完成一步 → df-review 评审该步 → 通过后再实施下一步。

## 输入

- 参数：change-id 和/或步骤号（如 `S2`），或明确的 diff 范围。
- 无参数：取 `docs/devflow/` 下最近变更的 design.md，找状态为"完成"且评审列非"通过"的步骤；全部步骤已完成时评审全量 diff。
- 找不到可评审对象时询问用户，禁止凭猜测圈定范围。

## 评审步骤

1. 圈范围：用 git diff 取该步改动，对照 impl-log.md 该步改动点清单；越出该步范围的改动单独指出。
2. 读上下文：design.md 该步方案要点、验收标准，以及被采纳的 D 决策点。

## 评审四层

1. 设计一致性：实现是否符合该步设计与决策点；有偏离时查是否有用户确认留痕，未留痕的偏离按 P1 报。
2. 通用工程质量：正确性、边界条件、并发与资源、错误处理、命名与可读性。
3. 当前仓库规范：AGENTS.md / 贡献指南（如有）的硬约束逐条对照。
4. 测试与验证完备：对照该步验收标准逐条核验，指出已验证什么、缺什么。

## 输出

- P0-P3 分级问题清单，每条带 `file:line` 证据与修复建议；没有问题的层也要写"未发现"，不省略。
- 结论：可进入下一步 / 须先修复（阻塞项 = P0/P1）。
- 收尾：通过时把 design.md 该步评审列改为"通过"；有问题保持"有疑问"并列出清单，等用户处置。

## 硬性约束

- 只评审不改码：用户要求修复时，提示用 `/df-implement` 处理后复审，评审者不亲手修。
- 证据先行：每个问题必须读码核实并给出 `file:line`；不确定的标"待确认"，不把猜测当结论。
- 文档与汇报语言跟随用户当前对话语言（默认简体中文）。
