# df-implement 实施

DevFlow 三步工作流的第三步：把获批的设计落成代码。多步设计一次只实施一步——小步交付，评审和测试都发生在小范围内。

## 前置校验

1. 定位 design.md：参数路径优先；无参数则在 `docs/devflow/` 下找最近修改的 `design.md`。不存在时停止，提示先走 `/df-design`。
2. 获批留痕：把 design.md 状态头改为 `状态: 已确认（YYYY-MM-DD，经 df-implement 调用批准）`。
3. 定步骤：
   - 参数指定了步骤（如 S2）：校验其依赖步骤状态为"完成"。
   - 无参数且多步设计：列出步骤总览，取下一个未开始且依赖已满足的步骤，向用户确认后执行。
   - 无参数且单步设计：直接执行 S1。
4. 依赖的前置步骤未完成时，停止并说明缺口，不跳步。
5. design.md 仍有未决决策点时，先逐条列出请用户拍板，再继续。

## 执行步骤

1. 只读 design.md 中该步的方案要点、验收标准，以及被采纳的 D 决策点结论；不扩大范围做相邻步骤的事。
2. 按影响面排序实施，大改动拆小提交粒度；若当前仓库存在代码生成链路，先改源文件并执行生成，再写业务代码。
3. 遵循当前仓库的工程规范（AGENTS.md、贡献指南等，如有）：最小改动面、注释与格式规范、生成链路、数据与配置约定。
4. 每完成一个可验证单元，立即执行其对应的最小验证；跨模块/公共结构变更时，同步构建所有受影响模块。
5. 对照该步验收标准逐条自检，再按当前仓库验证门禁（AGENTS.md/CI 约定，如有）收口；汇报列出实际执行的命令与 PASS/FAIL，禁止用一次全量构建充当唯一验证结论。
6. 该步完成时收尾：
   - 回写 design.md 步骤总览：该步 `状态: 完成`。
   - impl-log.md 追加该步小节（见模板）。
   - 向用户汇报：结论 → 改动点 → 验证证据 → 剩余风险，然后停止，提示 `/df-review S<该步>`；用户明示继续时才实施下一步。

## 协议变更处理

实施中发现必须改协议（S1 已冻结）：停下呈报，经确认后修改 design.md 的 S1 与协议版本记录，评估对已完成步骤的影响后再继续。禁止悄悄改。

## impl-log.md 模板（按步骤追加）

````markdown
# <change-id> 实施记录

状态: 进行中 | 完成 | 中断
上游: <design.md 路径>
日期: YYYY-MM-DD

## S1 <步骤名>

改动点：<文件 + 意图>
验证：<命令与 PASS/FAIL>
偏离：<与设计的偏离，无则写"无"；有则附用户确认方式>

## S2 …
````

## 硬性约束

- 偏离即停：实施中发现需要偏离设计（含设计漏项、代码事实冲突）时，停下呈报并等用户决定；禁止静默改设计。偏离被接受后回写 design.md。
- 中断恢复：重入先对账——按步骤总览与 impl-log 逐项核对已完成改动，对账结果先向用户呈现，再从断点续作，不重做已完成项。
- 未经用户明确要求不执行 git commit / push；子模块 checkout、pull、reset 一律禁止。
- 当前仓库若定义了代码生成产物（如 protobuf / 配置生成代码），只通过其生成脚本更新，禁止手改。
- 文档与汇报语言跟随用户当前对话语言（默认简体中文）。
