# df-analyze 需求分析

DevFlow 三步工作流的第一步：只负责把"粗糙需求"变成"事实清楚、缺口明确、可拍板"的分析文档。设计由 df-design 承接，实现由 df-implement 承接。

## 定位：补充而非替代

本技能是对模型原生分析能力的**额外补充**，不是思考边界：先用你自己的方式完整分析需求，再对照本技能核对系统性盲区（存量影响、是否开发、协作方）。模板与规则是底线不是上限，发现模板未覆盖的关键疑点、事实或风险时，自由增加小节——宁可多一节，不可漏一问。

## 输入

- 需求原文：对话中的文字描述，或用户给定的需求文件路径。
- 两者都缺失时，先向用户询问需求内容，禁止凭空编造需求。

## 前置：定位变更目录

1. 确定 change-id：`YYYYMMDD-<短英文slug>`（如 `20260920-order-export`）；用户已指定名称时用用户的。
2. 变更目录固定为 `docs/devflow/<change-id>/`，本步产物为其中的 `analysis.md`。
3. 目录已存在时视为续作：先读现有文档，在原有基础上修订，不得静默覆盖用户写过的内容。

## 执行步骤

1. 通读需求原文，拆出需求点清单，并标出明显缺口（没说清的对象、数量、边界、时机）。
2. 代码勘察：用 rg / 读码核实相关模块、接口、配置与数据的现状；每个关键结论必须附 `file:line` 证据；查不到的事实如实记为缺口，禁止臆测。
3. 按下方模板写出 `analysis.md`。
4. 向用户输出：分析摘要 + 决策点清单（每条附默认倾向），然后停止，等待拍板。

## analysis.md 模板

````markdown
# <change-id> 需求分析

状态: 草稿
上游: 无（原始需求见对话 / <需求文档路径>）
日期: YYYY-MM-DD

## 1. 背景与目标
## 2. 需求拆解（逐条编号）
## 3. 现状与事实（每条带 file:line 证据）
## 4. 影响面
- 协作方：纯后端 / 需客户端配合 / 跨服务 / 涉及第三方（df-design 据此判规模与 S1 协议前置）
- 存量影响：对已有数据、已有用户、已上线行为的兼容冲击；无则显式写"无"
- 常规：接口 / 协议 / 配置 / 数据 / 涉及模块
## 5. 疑问与决策点（编号 + 说明 + 默认倾向 + 影响）
（"是否开发"本身可作决策点：建议不开发 / 配置可解 / 本期不做，被采纳则流程终止）
## 6. 验收标准草案
## 7. 风险与事实缺口
````

## 硬性约束

- 只分析：不写设计方案、不修改业务代码、不执行生成脚本。
- 结束即停：决策点必须由用户逐条拍板；用户没有表态前，不得以"默认倾向"代替确认而自动进入下一步。
- 冲突上报：需求与代码事实冲突时列进决策点，不静默选择一方。
- 文档与汇报语言跟随用户当前对话语言（默认简体中文）。

## 下一步引导

决策点全部拍板后，提示用户：可执行 `/df-design`（参数给 analysis.md 路径）进入设计阶段。
