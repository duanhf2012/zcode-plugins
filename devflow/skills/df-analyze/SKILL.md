# df-analyze 需求分析

把"粗糙需求"变成"事实清楚、可拍板"的分析文档。设计归 df-design，实现归 df-implement。

## 原则：先思考，后对照

本技能不替代你的分析思考——先按你自身的最佳能力完整分析需求，再对照本技能收口。它只固定三件事：

- 产物契约：change-id 目录、analysis.md 模板、状态头；
- 盲区核对：存量影响、是否开发、协作方（大模型系统性易漏项）；
- 人工闸门：分析完停在决策点等拍板。

模板与规则是最低要求不是思考边界：模板外的关键疑点自由加节，宁可多一节不可漏一问；不要为填满模板而写，也不要因为模板没写就不想。

## 输入

需求原文 = 对话文字或文件路径；都没有则先问用户，禁止编造。

## 流程

1. change-id：`YYYYMMDD-<短英文slug>`（用户指定则从之），产物写 `docs/devflow/<change-id>/analysis.md`。目录已存在视为续作，修订而非覆盖。
2. 勘察：核实相关模块、接口、配置、数据现状，关键结论必须附 `file:line`；查不到的如实记为缺口，禁止臆测。
3. 产出 analysis.md，输出摘要 + 决策点清单（各附默认倾向），停止等拍板。

## analysis.md 模板

```markdown
# <change-id> 需求分析

状态: 草稿
上游: 无（原始需求见对话 / <路径>）
日期: YYYY-MM-DD

## 1. 背景与目标
## 2. 需求拆解
## 3. 现状与事实（带 file:line）
## 4. 影响面
- 协作方：纯后端 / 需客户端 / 跨服务 / 第三方（df-design 据此定规模与协议前置）
- 存量影响：对已有数据、用户、已上线行为的冲击；无则写"无"
- 接口 / 配置 / 数据 / 涉及模块
## 5. 疑问与决策点（编号 + 默认倾向；"是否开发"可作决策点，采纳即终止流程）
## 6. 验收标准草案
## 7. 风险与事实缺口
```

## 硬性约束

- 只分析：不出设计方案、不改业务代码。
- 结束即停：决策点须用户逐条拍板，不得以默认倾向代替确认。
- 需求与代码事实冲突列进决策点，不静默选择一方。
- 语言跟随用户（默认中文）。

拍板后提示：`/df-design` 进入设计。
